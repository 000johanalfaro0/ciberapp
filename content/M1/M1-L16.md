# Cron y tareas programadas: tu sistema trabajando solo

Tu computadora no necesita dormir. Tú sí.

Hay trabajos que conviene ejecutar a las 3 de la mañana, cuando nadie toca la máquina y los recursos sobran: copias de seguridad, rotación de logs, escaneos de puertos. Hacerlos a mano te obliga a quedarte despierto o, peor, a olvidarlos. Linux te deja programarlos una vez y olvidarte para siempre. Para eso existen dos mecanismos: uno para tareas **periódicas** (cron) y otro para servicios que arrancan **al encender** el equipo (rc scripts).

## El demonio: un proceso que vive en silencio

Un <a class="term" href="/glosario#demonio">demonio</a> (*daemon*) es un <a class="term" href="/glosario#procesos">proceso</a> que se ejecuta en segundo plano, sin interfaz, esperando su momento para actuar. No lo invocas tú directamente: vive ahí, vigilando. Imagínalo como el sereno de un edificio: está contratado para reaccionar cuando pasa algo, no para que lo veas trabajar. Linux está lleno de demonios, y uno de los más útiles es **crond**, el demonio del reloj.

## cron y crontab: programa una vez, ejecuta mil veces

<a class="term" href="/glosario#cron">cron</a> es el sistema de planificación de tareas de Linux. Tiene dos piezas que conviene no confundir:

- **crond**: el demonio que vive en segundo plano y revisa constantemente qué debe ejecutar.
- **crontab** (*cron table*): el archivo donde anotas QUÉ tarea, CUÁNDO y como QUÉ usuario.

crond lee crontab cada minuto. Si la hora coincide con una línea programada, ejecuta el comando; si no, sigue esperando. Simple y robusto.

## La anatomía de una línea crontab

Una entrada crontab tiene siete campos:

```
M  H  DOM  MON  DOW  USER  COMMAND
```

Los cinco primeros definen el CUÁNDO, el sexto el usuario y el séptimo la ruta absoluta del script o comando. Todo es numérico: marzo es `3`, no "March". La hora usa formato de 24 horas, así que la 1 pm es `13`.

| Campo | Unidad              | Valores                  |
|-------|---------------------|--------------------------|
| 1     | Minuto              | 0-59                     |
| 2     | Hora                | 0-23                     |
| 3     | Día del mes         | 1-31                     |
| 4     | Mes                 | 1-12                     |
| 5     | Día de la semana    | 0-7 (0 y 7 = domingo)    |

El asterisco `*` significa "todos". Un guion `-` define un rango: `1-5` es lunes a viernes. Una coma `,` enumera valores sueltos: `2,4` es martes y jueves.

## Ejemplos reales

Un backup cada domingo a las 2 am, ejecutado por el usuario `backup`:

```
00 2 * * 0 backup /bin/systembackup.sh
```

Se lee: minuto 00, hora 2, cualquier día del mes, cualquier mes, domingo (`0`), usuario backup, ejecuta ese script.

¿Solo los días 15 y 30 de cada mes?

```
00 2 15,30 * * backup /root/systembackup.sh
```

¿De lunes a viernes a las 11 de la noche?

```
00 23 * * 1-5 backup /root/systembackup.sh
```

¿Un escaneo MySQL solo los fines de semana del verano (junio a agosto), a las 2 am?

```
00 2 * 6-8 0,6 user /usr/share/MySQLscanner.sh
```

Aquí `6-8` acota los meses y `0,6` junta domingo y sábado.

## Cómo editar crontab

Para editar tu crontab personal:

```
crontab -e
```

La primera vez te pregunta qué editor quieres usar (nano, vim, etc.). También puedes abrir el archivo global directamente con tu editor favorito:

```
leafpad /etc/crontab
```

Ojo: `/etc/crontab` es el único crontab que incluye el campo `USER`; los crontab personales no lo necesitan porque ya saben de quién son.

## Atajos de crontab

Si la periodicidad es obvia, existen palabras clave que reemplazan los cinco campos de tiempo:

- `@yearly` / `@annually`
- `@monthly`
- `@weekly`
- `@daily` / `@midnight`
- `@noon`
- `@reboot` (al arrancar el sistema)

Por ejemplo, para correr un escaneo MySQL todas las noches a medianoche:

```
@midnight user /usr/share/MySQLscanner.sh
```

## rc scripts: que arranque solo al encender

cron ejecuta cosas cada cierto tiempo. Pero a veces no quieres periodicidad: quieres que un servicio arranque **una sola vez, al encender el equipo** y se quede corriendo. Para eso están los rc scripts.

Al iniciar Linux, el kernel carga sus módulos y luego lanza el demonio **init** (initd). init ejecuta una serie de scripts en `/etc/init.d/rc` que levantan los servicios necesarios: red, base de datos, servidor web, etc. Qué se arranca depende del <a class="term" href="/glosario#nivel-de-ejecucion">nivel de ejecución</a> (*runlevel*), un modo de operación que define qué servicios están activos:

- **0**: apagar el sistema
- **1**: monousuario (modo mínimo, sin red)
- **2-5**: multiusuario (modo normal)
- **6**: reiniciar

## update-rc.d: agrega servicios al arranque

Para decirle a init que un servicio arranque siempre al encender, usas `update-rc.d`:

```
update-rc.d postgresql defaults
```

Esto agrega PostgreSQL al rc.d. Tras reiniciar, el servicio levanta solo. Puedes comprobarlo buscando el proceso:

```
ps aux | grep postgresql
```

Si solo aparece tu propia línea de `grep`, es que no está corriendo aún; tras el reinicio aparecerá el proceso real. Si prefieres una interfaz gráfica, existe **rcconf**:

```
apt-get install rcconf
rcconf
```

Te muestra una lista de servicios: marcas con la barra espaciadora los que quieres al arranque, tabulas hasta OK y Enter.

## Cuándo usar cada uno

Regla práctica: si la tarea se **repite** en el tiempo (cada hora, cada día, cada mes), es para **cron**. Si la tarea debe **arrancar una vez al encender** y quedarse corriendo, es para **rc scripts**. Backups nocturnos: cron. Base de datos que necesita Metasploit al iniciar: rc.
